# Argo CD bootstrap for deployer → dev + orbstack

One command installs Argo CD on the **deployer** cluster and connects it to two
member clusters, so app deployments to development and production happen through
Git only.

```
                 ┌───────────────────────────────┐
   git push ───► │  github.com/fakabbir/          │
                 │  k8s-bootstrap (this repo)     │
                 └───────────────┬───────────────┘
                                 │ cloned over HTTPS by repo-server
                                 ▼
   kind-deployer   ══ Argo CD ══  application-controller, repo-server,
   (control plane)                server, applicationset-controller
              │
              ├──► dev-cluster     (kubectl context kind-dev)     development
              └──► orbstack-prod   (kubectl context orbstack)     production
```

| Role | kubectl context | Argo CD cluster name | Project |
|---|---|---|---|
| Runs Argo CD | `kind-deployer` | `https://kubernetes.default.svc` (in-cluster) | `argocd-system` |
| Development | `kind-dev` | `dev-cluster` | `dev` |
| Production | `orbstack` | `orbstack-prod` | `prod` |

Everything below `argocd/applications/` is synced by Argo CD itself through the
`argocd-root` app-of-apps, so projects and ApplicationSets follow Git after the
first bootstrap. `build.sh` only needs to be re-run for cluster changes.

## Prerequisites

- `kubectl`, `helm`, `jq`, `git`, and `base64` on the laptop; bash 3.2 or newer
  (macOS default works).
- The three contexts above already in `~/.kube/config`, answering
  `kubectl cluster-info`.
- This folder pushed to `https://github.com/fakabbir/k8s-bootstrap.git` on `main`.
  The repo must be **public**, or configured as a credential'd repository
  (see [Private repo](#private-repo-instead-of-public)).
- Argo CD's images pullable from the deployer cluster. A brand new kind cluster
  pulls ~250 MB, which is the slowest part of the first run.

Nothing is installed by this script outside Kubernetes: no argocd CLI, no helm
plugin, no cluster creation.

## Quick start

```bash
cd k8s-bootstrap
git init -b main && git remote add origin git@github.com:fakabbir/k8s-bootstrap.git
git add -A && git commit -m "Argo CD bootstrap" && git push -u origin main

./build.sh
```

Then open the UI:

```bash
kubectl --context kind-deployer -n argocd port-forward svc/argocd-server 8080:80
# http://localhost:8080  —  admin / password printed by build.sh
```

Expected at the end of `./build.sh`:

```
==> Result
  Clusters known to Argo CD
    dev-cluster      https://192.168.107.3:6443
    orbstack-prod    https://192.168.139.2:26443

  Applications (name / project / destination / sync / health)
    argocd-root   argocd-system    <none>         Synced  Healthy
    dev-demo-app  dev              dev-cluster    Synced  Healthy
    prod-demo-app prod             orbstack-prod  Synced  Healthy
```

Re-run any time; every step is idempotent and existing service account tokens are
reused rather than rotated.

## What build.sh does

1. **Preflight** — required binaries, all three contexts reachable, and the
   `main` branch of `GIT_REPO` visible. Fails here rather than half-installing.
2. **Install** — `helm upgrade --install` of `argo/argo-cd` (pinned version,
   values in `argocd/install/values.yaml`), waits for each component's rollout.
3. **Probe pod** — starts a throwaway `curl` pod in the deployer cluster and
   checks that in-cluster DNS resolves service names. Argo CD is made of service
   DNS names, so this catches a broken cluster before three CrashLoops do.
4. **Register each member cluster** — applies `argocd/clusters/manager-rbac.yaml`
   into it, reads the long-lived `argocd-manager` token, then probes candidate
   API addresses from inside the deployer cluster and applies a cluster Secret
   for whichever one authenticates. The rendered Secret lands in `.work/clusters/`
   (gitignored) because it carries a token.
5. **Apply the GitOps layer** — `AppProject argocd-system` then the `argocd-root`
   Application, waits for Synced/Healthy, then waits for the Applications
   generated by the ApplicationSets to be Synced/Healthy too.
6. **Report** — clusters, applications, and UI credentials.

Flags: `--skip-install`, `--skip-clusters`, `--skip-root`, `--help`.

## Reaching the member clusters from a laptop stack

This is the part that does not work by copy-pasting a kubeconfig, and it is what
`build.sh` figures out for you.

A pod inside `kind-deployer` cannot use the member cluster's kubeconfig address,
because both local runtimes publish their API on the laptop:

- kind publishes the API as `127.0.0.1:<random-port>` on the host. From a pod,
  `127.0.0.1` is the pod itself.
- OrbStack publishes it as `127.0.0.1:26443`, and its cluster IP `192.168.139.2`
  has nothing listening on `6443` — the port only exists on the laptop.

So the real addresses are the node IPs on the shared `kind` docker bridge:

```
dev-cluster    https://192.168.107.3:6443     node IP, API on its normal port
orbstack-prod  https://192.168.139.2:26443    machine IP, forwarded port from kubeconfig
```

`candidate_urls()` in build.sh derives exactly these from `kubectl get nodes`
plus the port in the kubeconfig, then lets the probe pod try them with the real
token and CA. Which address wins is recorded in `.work/clusters/<name>.json`, and
`argocd/clusters/cluster-secret.example.yaml` documents the shape. If you would
rather pin one, put it in the 4th field of `MANAGED_CLUSTERS`.

Both of those IPs are ephemeral (kind reassigns them when a cluster is
recreated), which is why the AppProjects and ApplicationSets refer to clusters by
**name** (`dev-cluster`, `orbstack-prod`) and never by URL. Re-running `build.sh`
after a cluster recreation re-points the names at the new addresses.

### If a cluster ends up registered as `insecure`

Argo CD verifies the member API certificate against the address it connects to.
`192.168.139.2` is an IP SAN on the OrbStack certificate, so verification works
here. If an address has no matching SAN, build.sh registers it with
`tlsClientConfig.insecure: true` and prints a warning. That is acceptable on a
laptop and not acceptable on a real cluster — fix the address or the certificate
instead.

## Day 2

**Add a workload to development**

```bash
mkdir -p apps/overlays/dev/api
$EDITOR apps/overlays/dev/api/kustomization.yaml   # resources: ../../../base  + patches
git add apps/overlays/dev/api && git commit -m "Add api to dev" && git push
```

The `dev-workloads` ApplicationSet notices the new directory within its poll
interval and creates `dev-api`, no Argo CD manifest changes needed. Any directory
under `apps/overlays/prod/` does the same on production.

**Promote to production** — copy or merge the change into
`apps/overlays/prod/<app>/` and push. Both ApplicationSets track `main`, so
promotion is a Git operation. To get a real PR gate, point the dev ApplicationSet
at a `develop` branch and the prod one at `main`.

**Check state without the UI**

```bash
kubectl --context kind-deployer -n argocd get applications
kubectl --context kind-deployer -n argocd get applicationsets
kubectl --context kind-deployer -n argocd get secret -l argocd.argoproj.io/secret-type=cluster
```

**Change the Argo CD install** — edit `argocd/install/values.yaml`, then
`./build.sh --skip-clusters --skip-root`.

**Add a third cluster** — append a line to `MANAGED_CLUSTERS`, add an AppProject
and ApplicationSet for it under `argocd/applications/`, and re-run `./build.sh`.

## Troubleshooting

**`argocd-repo-server` CrashLoops, or `dns: ... i/o timeout` in an Application**
In-cluster DNS on the deployer cluster is broken. With kind this is almost always
two clusters sharing the `kind` docker network with the same pod CIDR — kind's
default is `10.244.0.0/16` for every cluster, so two coredns replicas can both
own `10.244.0.3`. Give each cluster its own range
(`clusters/kind/deployer.yaml` uses `10.245.0.0/16` and service subnet
`10.97.0.0/16`) and recreate it:

```bash
kind delete cluster --name deployer
kind create cluster --config clusters/kind/deployer.yaml
./build.sh
```

Do not put the clusters on separate docker networks instead: Argo CD reaches the
member clusters through their node IPs on the shared bridge, which is what makes
the whole local setup work.

**`Argo CD could not reach <ctx> on any candidate address`**
The probe pod tried each derived address from inside the deployer cluster and none
answered. Check the mapping in [Reaching the member
clusters](#reaching-the-member-clusters-from-a-laptop-stack), find a working
address, and set it as the 4th field of `MANAGED_CLUSTERS` in
`config/bootstrap.env`. Common causes: the member cluster is not running, its API
is only bound to the laptop's loopback, or a VPN/firewall blocks the bridge.

**`answers but rejected the argocd-manager token`**
The address is fine; the RBAC is not. `argocd/clusters/manager-rbac.yaml` did not
apply cleanly, or the token secret predates the SA. Check
`kubectl --context <ctx> -n argocd get sa,secret` and, if the token is stale,
delete `argocd-manager-token` and re-run `./build.sh --skip-install --skip-root`.

**`argocd-root` stuck `Unknown` with a project or resource error**
The project whitelists are explicit. `argocd-system` only allows `AppProject` and
`ApplicationSet` in the `argocd` namespace, so a new kind of object under
`argocd/applications/` needs a matching whitelist entry. Note that Argo CD 3.5
whitelist entries take one `{group, kind}` per item (`kind: '*'` globs allowed),
and `spec.syncPolicy.retry.backoff.factor` is an integer, not a string.

**Application is OutOfSync after a push but nothing happens**
Argo CD polls Git every ~3 minutes. Force it from the UI, or delete the
Application's status refresh annotation:
`kubectl --context kind-deployer -n argocd patch application <name> --type merge -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"normal"}}}'`.

**A private repo instead of public**
The manifests use the anonymous HTTPS URL. For a private repo, keep that URL and
add credentials as a declarative repository Secret — either an HTTPS PAT or an SSH
deploy key:

```bash
kubectl --context kind-deployer -n argocd create secret generic repo-k8s-bootstrap \
  --from-literal=type=git --from-literal=url=https://github.com/fakabbir/k8s-bootstrap.git \
  --from-literal=username=x-access-token --from-literal=password=<PAT> \
  --from-literal=project=argocd-system \
  --label argocd.argoproj.io/secret-type=repository
```

Then add `repo-k8s-bootstrap` to `.work`-style hygiene: it holds a credential, so
never commit it. For SSH, generate a dedicated key, add the public half as a
repository deploy key with read access, and put `sshPrivateKey` in the same Secret
with `--from-literal=url=git@github.com:fakabbir/k8s-bootstrap.git`.

## Security notes

- **`argocd-manager` is bound to `cluster-admin`** in both member clusters, which
  is what lets Argo CD create Namespaces and read every app namespace. Narrow it
  by binding a custom ClusterRole; `argocd/clusters/manager-rbac.yaml` is the only
  place to change.
- **Tokens never enter Git.** They live in `.work/clusters/` (`chmod 600`) and in
  the cluster Secret on the deployer. `.work/` is gitignored; delete it when done.
- **The token does not expire** (static service account token Secret), which is
  why re-running the bootstrap is cheap. Rotate by deleting `argocd-manager-token`
  in the member cluster and re-running.
- **Argo CD UI is ClusterIP only**, reached by `port-forward`, with
  `server.insecure=true` so the forwarded endpoint is plain HTTP on a laptop
  network. Put TLS and a real SSO (re-enable `dex`) in front of it anywhere else.
- **`argocd-root` runs with `prune: true`**, so deleting a file under
  `argocd/applications/` and pushing deletes the project or ApplicationSet — and
  with an ApplicationSet, everything it generated.

## Teardown

```bash
# Argo CD and everything it manages on the deployer cluster
helm uninstall argocd --kube-context kind-deployer -n argocd
# Manager RBAC in the member clusters
for c in kind-dev orbstack; do kubectl --context $c delete -f argocd/clusters/manager-rbac.yaml; done
# Sample workloads, if they should go before the apps themselves do
kubectl --context kind-dev      -n demo delete ns demo
kubectl --context orbstack      -n demo delete ns demo
rm -rf .work
```

Deleting the `argocd` namespace on the deployer removes the apps on member
clusters only if their Applications are removed first, since Argo CD refuses to
delete the last thing managing them. Prefer the order above.
